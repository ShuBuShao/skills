# 翻新缺陷修复指引生成器

生成能独立使用的模块指引，让后续修复有明确的业务基线、取证入口和验证边界。通用流程留在技能中，项目事实只进入用户指定的项目文档。

## 识别输入与输出范围

从当前请求和工作区获取模块名称、目标实现目录、旧实现仓库或入口、输出位置，以及用户已确认的业务例外。参考文档是结构和经验来源，不自动成为其他模块的规则。

- 优先检索现有路由、菜单和源码补齐路径；不能只根据同名目录认定新旧对应关系。
- 未指定输出位置时，建议在目标业务目录使用 `AGENTS.md`；用户指定普通文档时遵从，并说明它不会自动作为目录指令加载。
- 多个不相邻模块分别生成；只有用户指定合并且作用域不会覆盖无关模块时才合并。
- 输出前读取目标文件和适用的上层 `AGENTS.md`、`CLAUDE.md`、项目规则与相关技能。更新时保留人工补充和已批准例外；冲突会改变规则含义时说明差异并询问。
- 找不到旧实现时，可交付明确注明缺失证据的调查指引，不编造路径或一致性结论。存在多个合理业务基线时，先询问再写入确定性规则。

## 提取事实

1. 记录各仓库的角色和当前工作树状态，区分目标实现、旧实现与路由转发宿主。
2. 从真实路由或页面入口追踪组件、模板、服务和接口封装；区分可达逻辑、旧入口、示例、注释和历史残留。已转发到新实现的旧 URL 不能冒充旧版运行证据。
3. 读取与模块相关的当前代码，提取修复时应查的接口、权限、语言资源和状态链路。生成指引不等于完成全模块业务审计。
4. 默认保持旧业务语义，同时记录已批准的新需求和契约变更。旧运行结果、源码与后端契约发生实质冲突时，列出证据并请求裁决，不机械套用来源排名。
5. 将项目规则引用到产物中。当前项目硬约束优先于参考文档经验；不能把跨项目规则冲突隐藏为“按需配置”。

## 提炼边界

保留可复用的方法：先证明缺陷与根因、对齐请求和状态语义、限制修复范围、检查共享调用方、区分静态与运行验证。

不推广个案结论：某参数必须为 `null`、某错误处理配置恒定正确、某业务状态一定失败、历史文档一律失效、特定浏览器或发布流程必须使用。它们只能在当前项目有依据时写入该项目产物。

公开技能不得包含用户工作区绝对路径、私有业务源码、凭据、Bug 编号或内部案例。生成到用户项目中的指引可以包含用户要求且已核实的路径；优先使用仓库相对路径，并交代跨仓库路径的基准。不要把项目的命令、权限边界或技能依赖硬编码进通用技能。

## 生成与更新

读取 [指引模板](assets/guide-template.md)，按取证结果替换编写提示并裁剪不适用项。模板是内容骨架，不做机械字符串替换。

- 指引开头写清适用目录、目标阶段、上层规则优先、取证日期与证据限度。
- 列出经核实的新旧入口与关键文件，说明关联仓库不会自动继承此文件。
- 将业务特殊检查项与通用流程分开，避免把新实现当前行为写成旧版事实。
- 请求对齐覆盖最终序列化、可选值语义、位置参数顺序和错误后的成功副作用；具体取值由当前调用链决定。
- 历史文档可作为线索；只有明确退出维护时才记录该状态，不擅自删除或停用。
- 保留当前用户授权与项目验证边界，不额外引入审批、部署、提交或自动修复流程。
- 更新已有文档时只修改已核实过时或本次要求调整的部分；未能复核的人工结论注明来源与限度，不静默覆盖。

## 验收与交付

检查路径存在、入口对应关系有源码依据、无未替换编写提示、无参考业务残留、没有覆盖上层规则。确认 `AGENTS.md` 只落在预期作用域。

至少检查正常生成、旧实现缺失、规则冲突和已有文档保留四种情形：缺失证据不能变成肯定结论；冲突不能被默认值掩盖；更新不能丢弃人工例外。

按文档改动运行适当的格式或差异检查，不为生成规则而执行真实业务写操作。交付文件链接、作用范围、已核实的证据和尚缺部分；生成指引通过不代表业务页面验证通过。是否提交、推送或安装技能由当前请求决定。
